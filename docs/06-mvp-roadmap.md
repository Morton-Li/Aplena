# Aplena MVP 路线图

## 1. 推进原则

- 每阶段都有可验证的完成定义，不以“代码大致存在”作为完成；
- `main` 只接收完整目标，阶段成果先经功能分支合并到 `develop`；
- 不提前实现没有当前用户价值的服务器、同步或会计概念；
- 领域公式、迁移、备份和历史不变量先于视觉扩展；
- 本地验证只证明对应范围，发布签名和 Windows 行为需要独立证据。

## 2. 第一阶段：规格与架构基线

目标：冻结产品边界、领域语义、逻辑 schema、关键流程、技术栈与决策理由。

交付物是本仓库 `README.md`、六份主体文档和四份 ADR。不生成应用脚手架，不安装依赖。

完成定义：

- 所有核心术语和公式在文档间一致；
- 双计入模式、自动初始化、NULL 实际、本位币锁定和承载能力有明确边界；
- 数据库字段、约束、索引、删除和迁移原则可直接转化为实现；
- 无派生统计表和前端直连 SQL；
- 路线图能够给出下一阶段的独立目标。

## 3. 第二阶段：可执行工程与领域内核

状态：已于 `feature/domain-foundation` 完成实现与本地验证。

本阶段建立了最小可运行的 Tauri 2 + React + Rust 工程，并优先实现不依赖 UI 的 PFCM
领域值对象、双计入规则和财务承载能力测试。锁文件、受限 IPC、结构化错误与最小真实命令
调用一并纳入基线；没有提前引入数据库或虚构 Dashboard 数据。

范围：

- 在开始前盘点本机已有 Node、pnpm、Rust、Xcode 工具链；
- 缺失依赖时停止并请求用户准备，不自行安装；
- 创建并锁定 Tauri、React、TypeScript、Vite 工程；
- 建立 Rust domain/application/infrastructure 分层；
- 实现 `YearMonth`、金额、汇率、类别、计入模式和承载能力纯函数；
- 完成月付、季度、半年、年付、一次性、跨年和零分母测试；
- 建立前后端 DTO 约定，但不实现完整页面和数据库。

完成定义：

- 开发构建在现有环境中可复现；
- Rust 领域测试全部通过；
- JavaScript/TypeScript 检查通过；
- 没有业务计算散落到 React；
- 没有数据库或 UI 为了演示而绕过领域层。

建议分支：`feature/domain-foundation`，完成后显式合并到 `develop`。

## 4. 第三阶段：SQLite 持久化与自动初始化

范围：

- 把逻辑 schema 转为 SQLx migrations；
- 启用 STRICT、外键、WAL 和约束触发器；
- 实现 Repository 和查询层；
- 实现 `ensure_month_initialized`、未来预览和历史补录；
- 实现 PlanItem CRUD、停止和删除行为；
- 实现数据库一致性与幂等集成测试。

完成定义：

- 全新和升级 migration 测试通过；
- 缺失汇率整批回滚；
- 重复初始化、项目改名和计划修改均不污染快照；
- 删除 PlanItem 保留 MonthlyItem；
- 本位币锁定不能绕过；
- schema 审计确认没有派生统计表。

建议分支：`feature/persistence-and-snapshots`。

## 5. 第四阶段：计划与月度执行界面

范围：

- 首次设置；
- 长期计划列表、表单和双模式预览；
- 本月自动初始化反馈；
- 月度实际表格、NULL/0 状态和备注；
- 按类别或整月批量确认；
- 结构化错误和无障碍基础。

完成定义：

- 核心流程可全键盘操作；
- 浏览历史或未来不产生写入；
- 保存、失败和重试状态明确；
- UI 自动化覆盖两种计入模式和 NULL/0；
- 所有权威金额来自 Rust 命令。

建议分支：`feature/planning-workflows`。

## 6. 第五阶段：Dashboard、历史、分析与承载能力

范围：

- 月度总览、实际完整度和重要偏差；
- 分类结构和项目横向排名；
- 历史收入、支出、结余和储蓄率；
- 两档新增长期承载能力、固定承诺率和责任覆盖率；
- PAYMENT 支付视图与月均承载口径说明；
- 图表 ARIA 和表格替代。

完成定义：

- 修改实际金额后相关查询自动失效并刷新；
- 所有聚合可从 MonthlyItem 重新计算；
- 数据不完整的月份不会被标记为最终实际；
- 零分母显示 N/A；
- PAYMENT 年付项目在非支付月仍进入承载能力；
- 图表与数值表结果一致。

建议分支：`feature/dashboard-and-capacity`。

## 7. 第六阶段：数据保护与 MVP 发布门禁

范围：

- 一致性备份、检查、恢复和 CSV 导出；
- migration 前恢复点；
- SQLCipher 与秘密存储的 macOS/Windows 技术验证；
- 日志隐私、CSP 和 Tauri capabilities 审计；
- macOS 签名、公证和安装验证；
- Windows 构建和安装验证；
- 崩溃恢复和损坏备份测试。

完成定义：

- 备份恢复后所有实体数、月份和聚合一致；
- 损坏或不兼容备份无法覆盖当前数据；
- 数据库静态加密方案得到真实签名构建证据；
- 发布包不具有非必要网络、Shell 或文件系统权限；
- 安装、升级、回滚和卸载路径有记录证据。

建议分支：`feature/release-hardening`。完成整个 MVP 目标并经过验收后，才显式把 `develop`
合并到 `main`。

## 8. MVP 总体验收

### 8.1 计划与快照

- 长期计划支持五个固定类别、两种计入模式和生效区间；
- 新月份自动初始化；
- 未来冻结和历史补录显式确认；
- 同一来源同月不重复；
- 计划、模式、周期和汇率变化不污染历史。

### 8.2 实际与分析

- NULL 和零实际不同；
- 批量确认不覆盖；
- Dashboard、历史和分析均动态查询；
- 收入和支出偏差采用正确语义；
- 实际完整度贯穿总览和趋势。

### 8.3 承载能力

- 使用固定收入和计划月均负担；
- 浮动收入不支撑新增固定承诺；
- 两档承载金额与比例可解释；
- 两种计入模式不会改变承载能力的月均口径；
- 零分母无误导输出。

### 8.4 数据保护

- 本位币锁定；
- 金额精确舍入；
- 恢复前预览和恢复点；
- 默认离线和最小权限；
- 迁移与备份可恢复；
- 历史快照在来源删除后保留。

## 10. 风险登记

| 风险 | 影响 | 对策/门禁 |
|---|---|---|
| 用户混淆均摊实际与支付实际 | 偏差失真 | 模式卡、字段文案、行内解释、预览测试 |
| 很久未打开导致历史月份缺失 | 历史不连续 | 只自动当前月；显式补录并提示汇率风险 |
| SQLCipher 跨平台打包复杂 | 发布受阻 | 第二/六阶段技术验证；未验证不得公开发布 |
| WebView 平台差异 | UI 或无障碍不一致 | macOS 首发，Windows 独立端到端门禁 |
| 金额溢出或重复舍入 | 数据错误 | Rust Decimal、范围校验、单次舍入、性质测试 |
| 提前冻结未来月份 | 未来计划陈旧 | 浏览不写入；显式预览和确认 |
| 派生数据被意外持久化 | 多事实来源漂移 | schema 审计和 Repository 边界测试 |
| 备份复制遗漏 WAL | 恢复损坏 | 在线备份/checkpoint，恢复完整性测试 |

## 11. 依赖与变更纪律

- 每阶段开始先检查现有工具链和工作树；
- 缺失本机依赖时请求用户准备或使用已授权测试环境，不擅自安装；
- 依赖使用锁文件并记录选择理由；
- 迁移、备份格式和 IPC 契约都进行版本控制；
- 不改变用户已有 staged/index 状态或无关工作；
- 不推送、部署、签名或发布，除非阶段目标明确授权。
