# ADR 0007：项目关联实际条目与显式完整状态

- 状态：接受
- 日期：2026-08-23
- 决策范围：月度实际事实、确认语义和计划外月份

## 背景

旧模型让用户直接编辑每个项目的月度实际总额，无法解释一笔退款、冲减或分多次收到/支付的情况，也无法区分“正在记录”和“已经核对”。把计划金额自动填成实际会制造没有发生过的事实。

同时，实际事件可能出现在没有正式计划快照的月份，例如结束后的退款。允许自由流水又会把产品推回传统记账软件。

## 决策

### 实际事实

新增 `ActualEntry`，且必须关联 `MonthlyItem`。条目包含日级日期、增加/减少效果、正两位金额、来源和备注。实际净额实时求和，不持久化月度实际总额。退款和冲减用减少效果表达，净额允许为负。

用户来源条目可增删改；旧聚合总额迁移为只读 `MIGRATED_AGGREGATE` 增加条目。条目不能改挂到另一月度项目，日期必须与所属月份一致。

### 完整状态

`actual_confirmed_at` 是独立核对标记：

- 无条目、未确认：`MISSING`；
- 有条目、未确认：`IN_PROGRESS`；
- 无条目、已确认：`CONFIRMED_ZERO`；
- 有条目、已确认：`FINAL`。

确认从不创建条目或复制计划金额。任何条目 CRUD 清除确认标记。

### 计划外月份

若现有计划在目标月无快照，系统创建 `ACTUAL_ONLY` 月度项目，计划金额为零。已结束但仍存在的计划允许迟到条目并提示；被删除而使快照来源为空的计划不能接收新条目。

若后续初始化认定该计划当月应正式计入，必须在初始化事务内原位提升 `ACTUAL_ONLY` 为 `PLANNED`，保留月度项目 ID、条目和确认事实。重复初始化幂等。

## 后果

- 月度 UI 必须把计划额和派生实际净额设为只读，提供全局和项目上下文两级条目入口；
- 分析、Dashboard 和历史都以条目为实际权威；
- 完整度由确认状态而非非空总额计算；
- 数据库需要第五张表、同月触发器、确认重开触发器和新增迁移；
- 条目仍被计划项目约束，产品不会演变为无分类自由流水账。

## 被否决方案

- 继续直接编辑聚合实际：无法保留退款和分次变更的解释；
- 支持用户公式：难以验证、迁移、审计和跨版本稳定；
- 用负数条目表达退款：增加输入错误和文案歧义；
- 确认时填入计划金额：把计划冒充实际；
- 为计划外事实创建自由流水：偏离产品定位；
- 初始化时删除仅实际项目再新建：会破坏条目外键和历史身份。
