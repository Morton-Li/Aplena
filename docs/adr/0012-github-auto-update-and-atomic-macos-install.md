# ADR 0012：GitHub 自动更新与 macOS 原子安装

状态：接受

## 背景

Aplena 的公开版本由 GitHub Releases 分发。要求后续稳定版能在应用内发现、下载和安装，同时继续使用项目现有的 “Morton Li” 自签名证书，不把 Developer ID、公证或云更新服务作为前置条件。公开 `v1.1.3` 尚未包含 updater，因此用户仍需手动安装一次桥接版本。

Tauri updater 的 minisign 验证可以证明下载字节由项目更新密钥签署，但它不能替代 macOS 应用身份验证。反过来，自签名代码证书也不能证明 GitHub 清单与下载包属于当前更新通道。两条信任链必须同时成立。

上游 `tauri-plugin-updater` 的 macOS 安装路径存在已公开的非原子替换风险：旧应用先被移动后，第二次移动失败可能让原安装路径消失。在该问题关闭并经本项目重新验证前，不能直接调用插件的 `Update::install`。

## 决策

1. 固定 `tauri-plugin-updater` 版本；只调用 `Update::download`，由插件完成 HTTPS 下载和 minisign 验证。
2. 正式构建编译进独立 updater 公钥；私钥与密码只存在于 GitHub `codesign` environment。流水线从已提交的最小 release 配置生成不入库的含公钥覆盖层，使运行时和 Tauri 打包器使用同一把公钥；缺少、错误或不匹配的密钥使严格标签构建失败。
3. 下载后的 `.app.tar.gz` 由仓库内 macOS 安装器处理。它限制压缩/展开大小、条目数量、固定发布包根目录和链接目标，并拒绝路径穿越及特殊 tar 条目；固定归档名与用户可能重命名的本机 `.app` 路径相互独立。
4. 新 `.app` 必须匹配 `li.morton.aplena`、清单版本、当前单一架构、`codesign --verify --deep --strict` 和固定自签名证书 SHA-256 指纹。
5. 临时目录必须位于已安装应用父目录并再次核对设备号。安装前重读原应用 inode/设备号，随后只允许 `renamex_np(..., RENAME_SWAP)` 原子交换。
6. 原子交换失败时不执行任何破坏性回退。成功后旧应用保留到下一次启动，再只清理由本安装器创建、属于当前用户、含 marker 且目录形状严格匹配的备份。
7. 自动行为仅限启动后检查。下载、安装和重启都需要用户操作；启动网络失败不阻塞本地财务功能。

## 结果

- 保持自签名不会因为 updater 本身而必然失败；实际安装仍取决于应用目录的当前用户写权限，更新后 macOS 也可能再次显示安全提示。
- 丢失 updater 私钥时，已有客户端无法信任新密钥。必须先用旧密钥发布嵌入新公钥的桥接版本；旧密钥已丢失时只能再做一次手动安装。
- 正式证书私钥、双架构包和 GitHub 最新稳定端点只能由远程严格标签流水线验证。本地临时 updater 密钥与模拟端点只用于隔离测试，不构成发布证据。
- 若未来采用 Developer ID、公证或上游修复，需要新的验证证据和显式 ADR，不得静默放宽当前双重验证与原子交换边界。
