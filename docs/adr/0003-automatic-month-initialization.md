# ADR-0003：当前自然月自动、历史与未来显式初始化

- 状态：Accepted
- 日期：2026-08-23

## 背景

电子表格版本需要用户手动创建新月份。Aplena 应消除这一步，但自动化不能静默补造历史、
提前冻结未来，也不能覆盖已经形成的月度事实。

## 决策

建立唯一业务操作：

```text
ensure_month_initialized(month, trigger, optional_rate_overrides)
```

自动触发：

- 应用启动并完成数据库迁移后，处理当前自然月；
- 新建 PlanItem 后，处理当前自然月。

显式触发：

- 用户确认初始化未来月份；
- 用户确认补录历史月份。

浏览历史或未来页面不触发写入。跨月未打开时，只自动处理重新打开时的当前月，不补造中间
历史月份。

## 原子性和幂等性

- 在一个写事务中读取、校验、计算和插入；
- 先验证全部应计项目，再进行首次插入；
- `UNIQUE(source_plan_item_id, month)` 是最终幂等屏障；
- 冲突只增加 `skipped`，不执行 UPDATE；
- 缺失汇率或非法计划导致整批回滚；
- 返回 `created`、`skipped`、`excluded` 和警告。

项目改名不改变来源 UUID，因此不会绕过幂等约束。修改计划或汇率也不会触发已有快照
更新。

## 零项目月份

当前月可能没有应计项目，尤其当所有计划都是非本月 PAYMENT。此时操作成功并返回零创建，
不为表示“初始化过”新增 MonthlyPeriod 实体。启动时重复检查是安全的；当前月后来新增适用
计划时，仍能补入缺失快照。

## 历史补录

历史补录必须先预览并说明：当前汇率不代表历史汇率。用户可以提供只用于本次转换的临时
汇率覆盖值。系统不保存历史汇率实体，只保存转换后的 MonthlyItem 金额。

## 未来初始化

未来月份只有在用户理解“冻结后不会随计划或汇率变化”并确认后才创建。普通预览通过
领域计算返回临时结果，不写数据库。

## 后果

正面：

- 正常跨月不再需要按钮；
- 重试和重复启动安全；
- 历史和未来不会因浏览被污染；
- 新增当月计划能自动补入。

代价：

- 长期不打开应用会产生需要用户处理的历史缺口；
- 自动初始化失败需要持久、可操作的 UI 提示；
- 零项目月份没有持久“已初始化”标记，会被安全地重复检查。

## 被拒绝的方案

- 每次打开任意月份都自动生成：会污染历史并过早冻结未来。
- 用项目名称防重复：改名后失效。
- 自动覆盖已存在行：破坏快照原则和用户实际数据。
- 新增 MonthlyPeriod 只记录空月：MVP 没有足够业务价值支撑额外实体。
