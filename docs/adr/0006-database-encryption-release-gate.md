# ADR 0006：首版数据库安全边界与未来静态加密

- 状态：Accepted
- 日期：2026-08-30
- 决策范围：首个正式版本的本地数据保护与静态加密路线

## 背景

Aplena 保存敏感的个人财务事实。应用当前使用 SQLx 0.9 的 `sqlite-bundled`，数据库、WAL 与 SHM 是普通 SQLite 文件。引入 SQLCipher 还需要更换底层 SQLite 链接方式，并为 macOS Keychain、Windows Credential Manager、错误密钥、迁移、崩溃恢复和真实发行包建立跨平台证据。

半成品加密可能导致密钥丢失、静默创建新库或无法恢复数据，因此不能为了获得“已加密”标签而在首版临时加入未验证的密码学与密钥管理。

## 决策

首个正式版本接受“本地优先、受当前操作系统用户权限保护，但数据库文件本身未静态加密”的 SQLite 安全边界。静态加密不再作为首版公开发布的硬阻断。

首版必须继续满足：

- 数据只保存在本机，不提供云账户、上传或银行同步；
- 数据目录权限为 `0700`，数据库、WAL 与 SHM 权限为 `0600`；
- 前端没有任意文件系统或数据库访问能力；
- 数据库路径、SQL、堆栈和内部诊断不进入前端错误协议；
- README 与发行文档明确说明数据库未静态加密，不声称端到端加密；
- 建议用户启用 FileVault 或等价的操作系统磁盘保护并保护本机账户。

## 已知风险

获得当前用户文件访问权限的恶意软件、已解锁账户中的其他进程或离线读取未加密磁盘的人，可能读取 SQLite 文件。Aplena 的文件权限不能抵御已经取得同一用户权限或管理员权限的攻击者。

这项风险被作为首版已知边界接受，而不是被描述为已经通过应用层加密解决。

## 未来增强方向

SQLCipher 与系统凭据存储仍是优先研究方向，但必须在独立分支和隔离数据库上验证：

1. macOS 与 Windows 均能创建、关闭并重新打开加密数据库；
2. 错误、缺失或被替换的密钥稳定 fail closed，不回退明文或创建新库；
3. WAL、迁移、崩溃中断、损坏检测、备份边界和升级回滚均有真实证据；
4. 发行包确认链接 SQLCipher，而不是普通 bundled SQLite；
5. Keychain 与 Credential Manager 行为在真实签名身份和用户会话中验证；
6. 密钥不进入日志、参数、环境变量、前端协议或崩溃材料。

未来若实现加密，必须单独设计从明文数据库到加密数据库的可恢复迁移；不得原地试验或静默修改现有用户数据。

## 被否决方案

- 自创文件加密格式或在 SQLite 外层手工加密页面；
- 把固定密钥、用户可猜测口令或明文密钥写入程序和配置；
- 首版加入没有跨平台恢复证据的“加密开关”；
- 在界面或 README 中把操作系统权限保护描述为数据库静态加密。
