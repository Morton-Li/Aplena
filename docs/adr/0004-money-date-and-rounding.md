# ADR-0004：固定精度金额、YearMonth 和单次 ROUND_HALF_UP

- 状态：Accepted
- 日期：2026-08-23

## 背景

汇率乘法和周期除法会产生不能用二进制浮点精确表示的小数。月份业务也不应受 UTC、本地
时区或每月天数影响。若前端、后端和数据库各自舍入，会产生不可解释的差异。

## 决策

### 金额

- 领域权威精度为四位小数；
- SQLite 保存放大 10,000 倍的 `INTEGER`；
- Rust 使用 `rust_decimal` 或经过同等验证的十进制类型；
- React 与 Rust 之间通过十进制字符串传递；
- JavaScript `number` 只用于有范围保护的最终图表显示，不回写。

### 汇率

- 权威精度为八位小数；
- SQLite 保存放大 100,000,000 倍的 `INTEGER`；
- 汇率严格大于零，本位币汇率精确为 1。

### 运算顺序

月度初始化：

```text
converted = decimal(source_amount) × decimal(rate)

AMORTIZED result = ROUND_HALF_UP(converted ÷ period_months, 4)
PAYMENT result   = ROUND_HALF_UP(converted, 4)
```

财务承载能力对两种模式都使用：

```text
ROUND_HALF_UP(converted ÷ period_months, 4)
```

不先把汇率乘积舍入再除周期。聚合对已落盘的缩放整数精确求和，不再次舍入金额。

用户输入实际金额时解析为十进制并按相同规则舍入到四位。负数非法；收支方向由类别表达。

### 月份

- 领域层使用 `YearMonth`；
- 数据库保存该月第一天 `YYYY-MM-01`；
- UI 只显示年月；
- 月份比较和加月由领域值对象完成；
- 聚合使用 `[month_start, next_month_start)`；
- 不把月初本地时间转换成 UTC 后再取月份。

## 溢出与范围

从字符串解析、乘汇率、除周期和转为缩放 64 位整数前都检查范围。溢出是输入验证错误，
不能截断、环绕或退化为浮点。前端格式化也必须处理超过 JavaScript 安全整数范围的金额。

## 后果

正面：

- 相同输入在不同平台得到相同快照；
- SQL 聚合没有浮点漂移；
- 月份不受时区和夏令时影响；
- 舍入规则可通过明确示例和性质测试验证。

代价：

- IPC 和表单不能直接把金额当普通 number；
- 图表层需要受控转换；
- 四位金额在 UI 中通常显示两位时，需要保留“显示精度不等于存储精度”的规则。

## 被拒绝的方案

- SQLite REAL 或 JavaScript number：存在二进制浮点误差。
- 用格式化字符串作为所有计算格式：聚合和排序成本高，约束弱。
- 每一步分别舍入：结果依赖运算拆分顺序。
- 用 UTC 时间戳存月份：会引入无业务价值的时区边界。
- 按实际月份天数分摊：PFCM 周期统一为月，不做按天权责计算。

## 验证

测试至少覆盖：

- `20 × 7.25 ÷ 12` 的确定结果；
- 正好位于半单位的 ROUND_HALF_UP；
- 非整除周期和大量项目求和；
- 最大合法金额与溢出拒绝；
- 12 月到下一年 1 月；
- 闰年不影响 YearMonth 加月；
- 前后端十进制字符串往返不改变值。
