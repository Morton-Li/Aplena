# Aplena 产品规格

状态：当前实现基线
适用版本：数据库 schema 4

## 1. 产品定位

Aplena 是本地优先的个人财务事实、计划与预算投影工具，不是银行流水账。用户可以直接建立本月项目并记录实际收入或支出；周期规则是可选增强，用于自动生成周期基准、偏差比较与下月预算投影。所有总额、图表和分析均由月度项目、实际条目或周期规则实时派生。

核心问题：

- 本月原计划如何，执行到哪里；
- 哪些项目偏离计划，偏离对收入或支出意味着什么；
- 收入、支出、结余与储蓄率如何变化；
- 固定承诺是否过重，下月预计能储蓄多少或存在多少缺口。

明确不做：

- 不导入或要求记录银行卡的每笔交易；
- 不导入无分类、无月度项目归属的自由流水；
- 不提供公式字段或会计分录系统；
- 不用当前长期计划或当前汇率回算历史月份。

## 2. 核心数据流

```text
PlanItem（可选） ──自动/显式初始化──┐
                                   ↓
用户直接创建本月项目 ─────────→ MonthlyItem
                                   ↑
                         ActualEntry（实际事实）
                                   ↓ 实时聚合
                        Dashboard / History / Analytics

PlanItem + ExchangeRate ──────────→ 下月预算投影（只读前瞻）
```

只有 `Settings`、`ExchangeRate`、`PlanItem`、`MonthlyItem` 和 `ActualEntry` 持久化。月度报告、总览、趋势、分类结构、项目占比和下月预算均为派生结果。

## 3. 设置与汇率

设置只包含本位币。本位币必须存在于汇率表且汇率恒为 1。下月预算月份由后端根据当前自然月计算，前端不能提交任意投影月份。

汇率定义为“1 单位原币 = N 单位本位币”，权威精度为八位小数。汇率只在创建 `PLANNED` 月度快照时读取；写入后的计划金额已换成本位币，不再联动。

已有任何月度快照后不得切换本位币，以防历史口径混合。

## 4. 下月预算与周期规则（可选增强）

“配置预算”页永远指向系统计算出的下一个自然月。页面直接根据可选周期规则派生预计收入、预计支出、预计储蓄和预计储蓄率，不接受独立储蓄目标。投影不实时作用于本月，不回写历史月，也不进入当前月或历史月的储蓄率比较。

周期规则不是启动、月度实际录入或基础报表的前置条件。它只在用户需要周期自动化、计划偏差或下月预算投影时启用。新增或修改规则不会自动创建或覆盖本月快照；新规则默认从下月第一日开始。

每个 `PlanItem` 包含：

- UUID、唯一规范化名称；
- 类别及由类别派生的收支方向；
- 非负、最多两位小数的原币计划金额；
- 币种、正整数周期（月）；
- `AMORTIZED` 或 `PAYMENT` 计入模式；
- 精确到日的开始日期和可空结束日期；
- 可空备注与审计时间。

类别固定为固定收入、浮动收入、必要支出、固定承诺支出、自主性预算。前两类派生为收入，其余派生为支出。

停止计划通过设置精确结束日期完成。删除只删除长期计划并将既有快照的来源置空；历史快照和条目不删除。

## 5. 两种计入模式

### 5.1 AMORTIZED

目标月的日期区间与计划有效日期区间有交集时，该月计入一次完整月均金额，不按有效天数比例折算：

```text
月均计划 = 原币金额 × 快照汇率 ÷ 周期（月）
```

开始日期在月末或结束日期在月初都仍代表该月有效。

### 5.2 PAYMENT

开始日期同时定义首次支付日和原始锚点日。每隔 `周期（月）` 计入完整金额：

```text
支付月计划 = 原币金额 × 快照汇率
```

短月将锚点日夹到该月最后一天，但后续长月恢复原始锚点。例如 1 月 31 日开始的月付计划依次落在 1 月 31 日、2 月 28/29 日、3 月 31 日。只有计划支付日期不晚于结束日期时才生成。

`MonthlyItem.scheduled_date` 只对 `PAYMENT` 的正式计划快照有值；`AMORTIZED` 与 `ACTUAL_ONLY` 均为空。

两种模式都按月均等价金额参与下月预算投影，避免年付项目只在支付月看起来有负担。

## 6. 月度初始化

应用启动时自动、幂等地补齐当前自然月。创建或修改周期规则不会自动补齐当前月。浏览其他月份不会写数据；未来月份和历史补录必须由用户显式确认。

初始化事务：

1. 读取目标月、计划、设置和所需汇率；
2. 按日级区间及计入模式判断是否生成；
3. 用十进制计算并只在最终本位币金额处执行一次 `ROUND_HALF_UP` 到分；
4. 写入独立 `PLANNED` 快照；
5. 以“来源计划 + 月份”保证幂等，不覆盖既有正式快照。

历史补录可提供只对本次初始化有效的临时汇率。缺少任何必要汇率时整月事务回滚。

## 7. 月度快照

`MonthlyItem` 冻结：来源计划引用（可空）、月份、项目名称、类别、收支方向、计入模式、来源类型、创建来源、计划支付日、计划金额、本位币和备注。

来源类型：

- `PLANNED`：由初始化生成的正式计划快照；
- `ACTUAL_ONLY`：为计划外月份的实际条目建立的零计划容器。

创建来源：

- `PLAN_LINKED`：来自长期计划或其计划外月份实际；
- `MANUAL`：用户直接创建的本月项目，不关联长期计划。

计划金额、币种和快照分类等均只读。实际净额、条目数、偏差和完成率均由实际条目派生，不作为独立权威总额保存。类目不设计确认或完成状态。

## 8. 实际条目

每条 `ActualEntry` 必须关联一个 `MonthlyItem`，包含：

- UUID 与月度项目 UUID；
- 精确到日且必须位于月度项目所属月份的日期；
- `INCREASE` 或 `DECREASE`；
- 严格大于零、最多两位小数的金额；
- `USER` 或 `MIGRATED_AGGREGATE` 来源；
- 可空备注与审计时间。

收入项目的文案为“收入 / 冲减”，支出项目为“支出 / 退款”。实际净额为增加条目之和减减少条目之和，因此允许出现负数。退款和冲减不通过负数金额表达。

用户条目可新增、编辑、删除。旧版聚合实际迁移得到的 `MIGRATED_AGGREGATE` 条目只读。

## 9. 手动月度项目与计划外事实

用户可以直接创建 `MANUAL + ACTUAL_ONLY` 临时类目，只需提供名称、类别、月份和可选备注。系统从类别派生收支方向，以当前本位币保存，计划金额固定为 `0.00`。此类项目进入实际收入、支出、净结余、分类结构与趋势，但没有计划基准，因此不生成计划偏差或完成率。用户可显式删除临时类目；服务只接受无计划来源的 `MANUAL + ACTUAL_ONLY`，并在同一事务中先删除其实际条目再删除类目。

用户可为仍存在的长期计划在没有正式计划快照的月份录入实际条目。系统先建立 `ACTUAL_ONLY` 月度项目，计划金额固定为 `0.00`。已结束但仍存在的计划允许接收迟到退款或冲减，并在界面提示；已删除计划不能接收新条目。

若后来初始化发现该计划应在该月正式计入，系统在同一事务中把现有 `ACTUAL_ONLY` 原位提升为 `PLANNED`：保持月度项目 UUID 和已有条目，仅补齐正式快照字段。重复初始化仍幂等。

## 10. 实际数据存在性

类目不具有确认、完成或处理中状态。没有实际条目时，派生实际保持 `null`；有条目时，派生实际等于增加条目之和减去减少条目之和，净额可以自然为零或负数。系统不会用计划金额补写实际，也不会为“零实际”创建虚假条目。

## 11. 派生计算

项目偏差：

```text
实际净额 - 计划金额（仅有计划基准时）
```

收入偏差大于零通常有利；支出偏差大于零通常不利。界面与 API 输出明确的业务效果，不能只用颜色解释正负号。

月度指标分别聚合收入和支出：

```text
净结余 = 总收入 - 总支出
储蓄率 = 净结余 ÷ 总收入
```

无收入或计划金额为零时不制造无效比例。手动月度项目不把零计划容器解释为真实预算。实际分析包含正式与仅实际月度项，减少条目会降低相应收入或支出。报表只说明实际是否存在及类目数量，不推导类目完成状态。

月度储蓄率只比较该月冻结计划与实际，提供百分点偏差和计划完成率；下月规则投影不得混入这一报表口径。

## 12. 下月预算投影

下月预算投影位于“配置预算”页，只计算下一个自然月。它按本位币月度等价金额汇总稳定收入、浮动收入、必要支出、固定承诺和自主性预算，并派生：

```text
预计收入 = 稳定收入 + 浮动收入
预计支出 = 必要支出 + 固定承诺 + 自主性预算
预计储蓄 = 预计收入 - 预计支出
预计储蓄率 = 预计储蓄 / 预计收入
```

预计储蓄允许为负，以直接暴露预算缺口；预计收入为零时储蓄率不可计算。固定承诺占稳定收入比例和稳定收入覆盖倍数保留为辅助指标。支出饼图只比较三类支出，不把收入与支出放在同一分母中；金额为零的类型不生成扇区。`PAYMENT` 项也以月均等价负担参与。没有周期规则时界面显示未启用，不把结果伪装成 `0.00`。图表与精确数据使用固定高度翻转，不因表格行数拉伸相邻卡片。

未来 Scenario 可在不改变正式计划的前提下模拟收入下降或新增/减少支出；它不属于当前持久化模型。

## 13. 页面与主流程

- 总览：当前月冻结计划、实际、重要偏差、结构与历史趋势；
- 月度执行：当前月或从历史报告明确选中的月份，其计划/实际净额只读展示，并提供临时类目维护、上下文条目维护和显式初始化；
- 历史报表：进入任意已有月份查看完整月度明细，并可明确进入该月或该项目的实际条目调整工作台；
- 配置预算：下月预算概览、支出类型占比，以及周期规则的预览、新建、编辑和删除；
- 设置：本位币、当前汇率，以及是否在每次启动时自动更新官方汇率。

主流程是进入当月、按需要创建临时类目并记录实际结果。需要查看下月预算结果或配置周期自动化时，用户再进入“配置预算”页；这些操作不会改写本月。用户不需要每天记账。

## 14. 数据兼容

- 首个公开版以 `0001_initial_release.sql` 建立 schema 1；schema 2 追加移除月度类目确认字段与重开触发器；schema 3 直接删除 `next_month_goal` 表及其中旧目标数据，不提供兼容读取；schema 4 保存启动时自动更新汇率偏好；
- 公开兼容性从 schema 1 开始，已发布数据库变更只能追加新迁移；
- 预发布迁移链不属于公开兼容范围，现有本地预发布数据必须按独立换轨方案复制到全新基线，不能改写旧库迁移历史；
- 发现高于当前应用支持范围的 schema 时拒绝启动，不降级写入；
- 迁移由 SQLx 在数据库事务中执行，失败不进入应用业务流程。

## 15. 验收原则

1. 月度项目是实际条目入口，长期计划不得成为强制前置条件；
2. 历史计划快照不被未来计划、汇率或删除污染；
3. 金额在所有持久化、IPC 与 UI 边界保持两位权威精度；
4. 日级有效期、月末支付锚点和结束日边界可由测试复现；
5. 临时类目创建/删除、条目 CRUD、退款/冲减、仅实际及原位提升均有自动测试；
6. 派生分析无需手动刷新且不持久化副本；
7. 全新数据库只执行正式基线；预发布本地数据经授权的隔离换轨后可保持业务事实等价。
8. 周期规则变更不会修改当前月或历史月快照与分析，下月投影允许显示负储蓄。
