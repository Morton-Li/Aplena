# Aplena 产品规格

状态：当前实现基线
适用版本：数据库 schema 4

## 1. 产品定位

Aplena（Personal Financial Capacity）是本地优先的个人财务事实、计划与承载能力工具，不是银行流水账。用户可以直接建立本月项目并记录实际收入或支出；长期计划是可选增强，用于自动生成周期基准、偏差比较与财务承载能力。所有总额、图表和分析均由月度项目及实际条目实时派生。

核心问题：

- 本月原计划如何，执行到哪里；
- 哪些项目偏离计划，偏离对收入或支出意味着什么；
- 收入、支出、结余与储蓄率如何变化；
- 固定承诺是否过重，还能承担多少长期支出。

明确不做：

- 不导入或要求记录银行卡的每笔交易；
- 不导入无分类、无月度项目归属的自由流水；
- 不提供公式字段或会计分录系统；
- 不用当前长期计划或当前汇率回算历史月份。

## 2. 核心数据流

```text
PlanItem（可选） ──自动/显式初始化──┐
                                   ↓
用户直接创建本月项目 ─────────→ MonthlyItem
                                   ↑
                         ActualEntry（实际事实）
                                   ↓ 实时聚合
                        Dashboard / History / Analytics
```

只有 `Settings`、`ExchangeRate`、`PlanItem`、`MonthlyItem` 和 `ActualEntry` 持久化。月度报告、总览、趋势、分类结构和项目占比均为派生结果。

## 3. 设置与汇率

设置包含目标月份、本位币和最低储蓄率。月份在 IPC 使用 `YYYY-MM`，数据库使用当月第一日作为锚点。本位币必须存在于汇率表且汇率恒为 1。

汇率定义为“1 单位原币 = N 单位本位币”，权威精度为八位小数。汇率只在创建 `PLANNED` 月度快照时读取；写入后的计划金额已换成本位币，不再联动。

已有任何月度快照后不得切换本位币，以防历史口径混合。

## 4. 长期计划（可选增强）

长期计划不是启动、月度实际录入或基础报表的前置条件。它只在用户需要周期自动化、计划偏差或承载能力分析时启用。

每个 `PlanItem` 包含：

- UUID、唯一规范化名称；
- 类别及由类别派生的收支方向；
- 非负、最多两位小数的原币计划金额；
- 币种、正整数周期（月）；
- `AMORTIZED` 或 `PAYMENT` 计入模式；
- 精确到日的开始日期和可空结束日期；
- 可空备注与审计时间。

类别固定为固定收入、浮动收入、必要支出、固定承诺支出、自主性预算。前两类派生为收入，其余派生为支出。

停止计划通过设置精确结束日期完成。删除只删除长期计划并将既有快照的来源置空；历史快照和条目不删除。

## 5. 两种计入模式

### 5.1 AMORTIZED

目标月的日期区间与计划有效日期区间有交集时，该月计入一次完整月均金额，不按有效天数比例折算：

```text
月均计划 = 原币金额 × 快照汇率 ÷ 周期（月）
```

开始日期在月末或结束日期在月初都仍代表该月有效。

### 5.2 PAYMENT

开始日期同时定义首次支付日和原始锚点日。每隔 `周期（月）` 计入完整金额：

```text
支付月计划 = 原币金额 × 快照汇率
```

短月将锚点日夹到该月最后一天，但后续长月恢复原始锚点。例如 1 月 31 日开始的月付计划依次落在 1 月 31 日、2 月 28/29 日、3 月 31 日。只有计划支付日期不晚于结束日期时才生成。

`MonthlyItem.scheduled_date` 只对 `PAYMENT` 的正式计划快照有值；`AMORTIZED` 与 `ACTUAL_ONLY` 均为空。

两种模式都按月均等价金额参与财务承载能力计算，避免年付项目只在支付月看起来有负担。

## 6. 月度初始化

应用启动时自动、幂等地补齐当前自然月。创建或修改计划后，系统也会自动补齐当前自然月缺失的正式快照。浏览其他月份不会写数据；未来月份和历史补录必须由用户显式确认。

初始化事务：

1. 读取目标月、计划、设置和所需汇率；
2. 按日级区间及计入模式判断是否生成；
3. 用十进制计算并只在最终本位币金额处执行一次 `ROUND_HALF_UP` 到分；
4. 写入独立 `PLANNED` 快照；
5. 以“来源计划 + 月份”保证幂等，不覆盖既有正式快照。

历史补录可提供只对本次初始化有效的临时汇率。缺少任何必要汇率时整月事务回滚。

## 7. 月度快照

`MonthlyItem` 冻结：来源计划引用（可空）、月份、项目名称、类别、收支方向、计入模式、来源类型、创建来源、计划支付日、计划金额、本位币和备注。

来源类型：

- `PLANNED`：由初始化生成的正式计划快照；
- `ACTUAL_ONLY`：为计划外月份的实际条目建立的零计划容器。

创建来源：

- `PLAN_LINKED`：来自长期计划或其计划外月份实际；
- `MANUAL`：用户直接创建的本月项目，不关联长期计划。

计划金额、币种和快照分类等均只读。实际净额、条目数、偏差、完成率和状态均由条目与确认标记派生，不作为独立权威总额保存。

## 8. 实际条目

每条 `ActualEntry` 必须关联一个 `MonthlyItem`，包含：

- UUID 与月度项目 UUID；
- 精确到日且必须位于月度项目所属月份的日期；
- `INCREASE` 或 `DECREASE`；
- 严格大于零、最多两位小数的金额；
- `USER` 或 `MIGRATED_AGGREGATE` 来源；
- 可空备注与审计时间。

收入项目的文案为“收入 / 冲减”，支出项目为“支出 / 退款”。实际净额为增加条目之和减减少条目之和，因此允许出现负数。退款和冲减不通过负数金额表达。

用户条目可新增、编辑、删除。旧版聚合实际迁移得到的 `MIGRATED_AGGREGATE` 条目只读。任何条目新增、编辑或删除都会清除所属项目的最终确认标记。

## 9. 手动月度项目与计划外事实

用户可以直接创建 `MANUAL + ACTUAL_ONLY` 月度项目，只需提供名称、类别和月份。系统从类别派生收支方向，以当前本位币保存，计划金额固定为 `0.00`。此类项目进入实际收入、支出、净结余、分类结构与趋势，但没有计划基准，因此不生成计划偏差或完成率。

用户可为仍存在的长期计划在没有正式计划快照的月份录入实际条目。系统先建立 `ACTUAL_ONLY` 月度项目，计划金额固定为 `0.00`。已结束但仍存在的计划允许接收迟到退款或冲减，并在界面提示；已删除计划不能接收新条目。

若后来初始化发现该计划应在该月正式计入，系统在同一事务中把现有 `ACTUAL_ONLY` 原位提升为 `PLANNED`：保持月度项目 UUID、已有条目和确认事实，仅补齐正式快照字段。重复初始化仍幂等。

## 10. 实际数据完整状态

确认表示“这些条目已经核对完成”，不等于把计划值复制成实际值：

| 条目 | 已确认 | 状态 | 派生实际 |
|---:|---:|---|---:|
| 0 | 否 | `MISSING` | 空 |
| >0 | 否 | `IN_PROGRESS` | 条目净额 |
| 0 | 是 | `CONFIRMED_ZERO` | `0.00` |
| >0 | 是 | `FINAL` | 条目净额 |

可确认单个项目，也可按整月或类别确认。旧的“用计划金额填补缺失实际”行为不存在。

## 11. 派生计算

项目偏差：

```text
实际净额 - 计划金额（仅有计划基准时）
```

收入偏差大于零通常有利；支出偏差大于零通常不利。界面与 API 输出明确的业务效果，不能只用颜色解释正负号。

月度指标分别聚合收入和支出：

```text
净结余 = 总收入 - 总支出
储蓄率 = 净结余 ÷ 总收入
```

无收入或计划金额为零时不制造无效比例。手动月度项目不把零计划容器解释为真实预算。实际分析包含正式与仅实际月度项，减少条目会降低相应收入或支出。完整度由最终确认状态计算，而不是由是否存在一个总额字段判断。

储蓄率同时提供百分点偏差、目标完成率和相对偏离，产品文案必须区分三者。

## 12. 财务承载能力

承载能力是启用长期计划后提供的增强分析，直接基于当前长期计划而非历史快照，计算稳定收入、浮动收入、必要支出、固定承诺、自主预算、保守可用空间和最大可用空间。`PAYMENT` 项也以月均等价负担参与。没有长期计划时界面显示未启用，不把结果伪装成 `0.00`。

未来 Scenario 可在不改变正式计划的前提下模拟收入下降或新增/减少支出；它不属于当前持久化模型。

## 13. 页面与主流程

- Dashboard：目标月总览、重要偏差、结构与趋势；
- 月度计划：只读计划/实际净额、两级条目维护、确认状态、显式初始化；
- 长期计划（可选）：日级开始/结束日期、两种计入模式、预览、新建、编辑、停止、删除；
- 历史与分析：按月、分类和项目查看派生结果；
- 设置：目标月、本位币、汇率与储蓄目标。

主流程是进入当月、直接创建月度项目并按需要记录实际结果、月底确认完成。需要周期自动化或承载能力时，用户再维护长期计划；应用自动为当前月补齐计划快照。用户不需要每天记账。

## 14. 数据兼容

- 数据库只有追加迁移；schema 3 把旧四位缩放整数按 `ROUND_HALF_UP` 转为分，schema 4 增加月度项目创建来源；
- 旧计划月锚点变为对应日期，旧实际空值保持未确认，零值成为确认零，正值成为只读迁移条目；
- 发现高于当前应用支持范围的未来 schema 时拒绝启动，不降级写入；
- 迁移由 SQLx 在数据库事务中顺序执行，失败不进入应用业务流程。

## 15. 验收原则

1. 月度项目是实际条目入口，长期计划不得成为强制前置条件；
2. 历史计划快照不被未来计划、汇率或删除污染；
3. 金额在所有持久化、IPC 与 UI 边界保持两位权威精度；
4. 日级有效期、月末支付锚点和结束日边界可由测试复现；
5. 手动月度项目、条目 CRUD、确认、退款/冲减、仅实际及原位提升均有自动测试；
6. 派生分析无需手动刷新且不持久化副本；
7. 旧数据库可以无损前向进入当前模型。
