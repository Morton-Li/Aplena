# Aplena 产品规格

- 状态：已接受的第一阶段基线
- 日期：2026-08-23
- 产品名称：Aplena — Personal Financial Capacity
- 内部模型：PFCM（Personal Financial Capacity Model）

## 1. 产品定义

Aplena 是面向个人的长期财务规划与执行跟踪软件。它不要求用户记录每笔交易，而是维护
长期收入和支出计划，把适用于某个月的计划冻结为独立快照，然后由用户更新项目级实际
金额。

产品持续回答两个核心问题：

1. 当前计划执行得怎样，偏差在哪里？
2. 当前稳定收入还能合理承担多少新的长期支出？

## 2. 目标用户与使用边界

MVP 面向希望降低财务维护成本、但仍需要长期规划和结构分析的单个用户。每个应用数据集
只包含一个财务账本。

MVP 明确不包含：

- 逐笔流水、复式记账或会计科目；
- 银行账户连接、支付或自动导入交易；
- 云端账户、跨设备同步和多人协作；
- 自动获取汇率；
- AI 投资建议、税务建议或信用决策；
- 持久化 Scenario；
- 移动端。

## 3. 术语

| 产品术语 | 代码术语 | 定义 |
|---|---|---|
| 长期计划 | `PlanItem` | 未来月份初始化的权威输入 |
| 月度快照/月度项目 | `MonthlyItem` | 初始化时冻结的计划事实及其实际金额 |
| 计入模式 | `RecognitionMode` | 月度均摊或按支付月计入 |
| 当前自然月 | `current_month` | 按本机本地日历得到的当月 |
| 目标月份 | `target_month` | 当前操作和 Dashboard 默认展示的月份 |
| 本位币 | `base_currency` | 月度快照使用的统一币种 |
| 月均负担 | `monthly_equivalent` | 原币计划金额乘汇率后除以周期月数 |

日期只表达月份时，领域层统一使用 `YearMonth`。数据库表示统一为当月第一天
`YYYY-MM-01`，不携带时区或日内时间。

## 4. 分类与收支方向

类别固定，不允许用户扩展或改变映射：

| 类别 | 收支方向 |
|---|---|
| 固定收入 | 收入 |
| 浮动收入 | 收入 |
| 必要支出 | 支出 |
| 固定承诺支出 | 支出 |
| 自主性预算 | 支出 |

分类是领域规则而不是用户可编辑的 Enums 表。映射只在 Rust 领域层定义一次，UI 读取
后端提供的选项和标签，数据库使用约束保护合法组合。

## 5. 数据流和历史边界

```text
Settings + ExchangeRate + PlanItem
                  ↓ ensure_month_initialized
              MonthlyItem
                  ↓ 实时查询与聚合
Dashboard / Monthly Report / History / Analytics

PlanItem（当前长期计划）
                  ↓ 月均标准化
       Financial Capacity（未来承载能力）
```

核心持久化实体只有：

- `Settings`
- `ExchangeRate`
- `PlanItem`
- `MonthlyItem`

Dashboard、Monthly Report、趋势、项目占比和分类结构均不建立持久化副本。

月度快照创建后：

- 修改或删除长期计划不修改或删除快照；
- 修改汇率、本位币以外的设置或周期不重算快照；
- 后续自动初始化只创建缺失记录；
- 只有实际金额和月度备注可由普通编辑流程维护。

## 6. 设置与汇率

### 6.1 目标月份

`target_month` 是 Dashboard 和月度计划默认操作月份。应用正常启动时将它归一化到当前
自然月；历史浏览使用页面月份参数，不触发月度初始化。

用户可以显式选择未来月份并执行“初始化未来月份”，但仅仅浏览未来月份不会冻结数据。

### 6.2 本位币

- 必须存在于 `ExchangeRate`；
- 对应汇率必须等于 1；
- 第一个 `MonthlyItem` 创建后锁定；
- MVP 不允许把一个账本的历史整体换算成另一币种。

### 6.3 汇率

汇率定义为：

```text
1 单位外币 = N 单位本位币
```

汇率只在创建月度快照或计算当前承载能力时读取。月度快照只保存已经转换的金额和当时的
本位币，不与之后的汇率联动。

## 7. 长期计划

`PlanItem` 至少包含：

- 用户不可见的稳定 UUID；
- 唯一、非空的人类可读名称；
- 固定类别和由其派生的收支方向；
- 非负计划金额及其币种；
- 大于零的正整数周期（月）；
- 计入模式；
- 首次计入月份；
- 可空的最后计入月份；
- 备注。

保存前对名称执行 Unicode NFKC 规范化和首尾空白清理。结束月份不得早于首次计入月份。
不增加 `Enabled`；停止长期计划通过填写结束月份完成。

## 8. 双计入模式

先定义月份是否位于有效区间：

```text
effective(m) = start_month <= m
               AND (end_month IS NULL OR m <= end_month)
```

### 8.1 月度均摊 `AMORTIZED`

每个有效月份都生成月度快照：

```text
planned_amount = source_amount × exchange_rate ÷ period_months
```

实际金额表示同口径的月度归一化实际负担。例如 6,600 元年付保险应填写为每月 550 元，
而不是在付款月填写 6,600 元。

### 8.2 按支付月计入 `PAYMENT`

`start_month` 是第一次支付或第一次计入的月份。仅在满足下式时生成：

```text
effective(m)
AND months_between(start_month, m) % period_months = 0
```

生成金额为：

```text
planned_amount = source_amount × exchange_rate
```

非支付月份不生成零金额记录。实际金额表示该支付月真实发生的现金收入或支出。

### 8.3 示例和边界

假设首次计入月份为 2026-01，最后计入月份为空：

| 周期 | `AMORTIZED` | `PAYMENT` |
|---:|---|---|
| 1（月付） | 每月为原金额 | 每月为原金额 |
| 3（季度） | 每月为原金额 ÷ 3 | 1、4、7、10 月为原金额 |
| 6（半年） | 每月为原金额 ÷ 6 | 1、7 月为原金额 |
| 12（年付） | 每月为原金额 ÷ 12 | 每年 1 月为原金额 |

一次性项目使用 `PAYMENT`，令 `start_month = end_month`，周期填写 1。若支付周期跨过
`end_month`，结束月份之后不再生成。

模式、金额、周期和日期的修改只影响尚未生成的月份。`MonthlyItem` 复制生成时的
`recognition_mode`，使历史显示保留当时口径。

## 9. 月度自动初始化

系统提供统一的幂等操作：

```text
ensure_month_initialized(month, trigger, optional_rate_overrides)
```

自动触发场景：

1. 数据库打开且迁移成功后，检查当前自然月；
2. 新建长期计划成功后，检查它是否应计入当前自然月。

显式触发场景：

- 用户确认初始化未来月份；
- 用户确认补录历史月份。

普通历史或未来页面浏览不触发初始化。

执行步骤：

1. 在写事务中读取设置、汇率和有效计划；
2. 校验本位币、汇率、金额、周期和月份；
3. 按计入模式判断是否生成并进行一次最终舍入；
4. 用 `source_plan_item_id + month` 唯一约束插入缺失记录；
5. 已存在记录只计入 `skipped`，绝不更新；
6. 任一应生成项目校验失败时整批回滚；
7. 返回 `created`、`skipped`、`excluded` 和可展示的错误。

当前月没有应计项目时不创建额外月份实体。每次启动可以安全地再次得到
`created = 0`；以后新增适用计划时，同一操作仍会补入缺失项目。

如果应用跨月未打开，系统只自动初始化重新打开时的当前自然月，不静默补造缺失历史。
历史补录必须展示汇率口径风险；用户可在确认页提供仅用于本次转换的临时汇率覆盖值，
该汇率不作为历史实体保存，最终仅保存转换后的月度金额。

## 10. 月度实际维护

初始化后：

```text
actual_amount = NULL  尚未录入
actual_amount = 0     已确认实际为零
actual_amount > 0     已录入实际值
```

Dashboard 必须显示实际数据完整度，例如“12/18 项已更新”。实际数据不完整时，实际总额
标记为“当前已录”，趋势点使用未完成视觉状态，不宣称为最终结果。

提供按项目、类别或整月执行“将未录项目按计划确认”的操作；它只填充 NULL，不覆盖已经
填写的实际金额。

## 11. 动态报告与偏差语义

所有月份统计采用半开区间：

```text
month <= date < next_month
```

原始偏差统一为：

```text
actual_amount - planned_amount
```

UI 按收支方向解释：

- 收入：多收入或少收入；
- 支出：超支或节省。

收入项目使用“达成率”，支出项目使用“预算使用率”。计划金额为零时比率为 `N/A`。

总览指标包括计划与实际的总收入、总支出、净结余和储蓄率。实际收入为零时实际储蓄率为
`N/A`。储蓄率同时显示百分点差；计划储蓄率大于零时才显示目标完成率和相对偏离。

## 12. 财务承载能力

承载能力直接从当前有效 `PlanItem` 和当前汇率计算，不读取月度支付峰值。无论项目选择
哪种计入模式，都先换算为月均金额：

```text
monthly_equivalent = source_amount × exchange_rate ÷ period_months
```

定义：

```text
S = 固定收入月均计划金额
N = 必要支出月均计划金额
C = 固定承诺支出月均计划金额
D = 自主性预算月均计划金额
r = 最低目标储蓄率
```

指标：

```text
保持现有自主预算时的新增承载能力 = MAX(0, S × (1-r) - N - C - D)
压缩自主预算后的极限承载能力   = MAX(0, S × (1-r) - N - C)
固定承诺率                     = C ÷ S
基础责任覆盖率                 = S ÷ (N + C)
```

浮动收入作为潜在上行单独展示，不用于支撑新的长期固定承诺。`S = 0` 时固定承诺率为
`N/A`；`N + C = 0` 时基础责任覆盖率为 `N/A`。不得用无穷大或误导性的 0% 代替。

## 13. 数据保护与纠错

普通月度编辑只允许修改实际金额和月度备注。快照中的项目名称、月份、类别、收支方向、
计入模式、计划金额和本位币均为系统字段。

如果当前或未来月份初始化配置有误，只有在该月所有实际金额仍为 NULL 时，才允许经过
二次确认撤销该月快照，并在操作前创建恢复点。已录入实际数据的月份不得通过普通流程
重建。

## 14. MVP 功能清单

- 首次设置、本位币和最低目标储蓄率；
- 手动汇率维护；
- 长期计划新建、编辑、停止和删除确认；
- 当前月自动初始化、未来显式初始化、历史显式补录；
- 月度实际金额和备注维护、批量按计划确认；
- 当月总览、偏差、数据完整度；
- 收支结构、项目排名和历史趋势；
- 可解释的财务承载能力；
- 本地备份、恢复和 CSV 导出。

## 15. 产品验收不变量

1. 项目改名不会导致同一来源在同月重复生成。
2. 重复初始化只创建缺失快照，不覆盖已有值。
3. 计划、周期、模式或汇率变化不重算历史。
4. 删除长期计划不会删除历史月度快照。
5. 未录实际和确认零值在存储、查询和 UI 中都不同。
6. 本位币锁定后不能产生混币历史趋势。
7. 支付模式的长期项目仍完整进入月均承载能力。
8. 所有零分母指标返回 `N/A`。
9. 没有派生统计表成为第二数据源。
